# Responses continuation ownership

`previous_response_id` is an upstream response reference, not a cache-prefix
affinity hint. A short incremental request can match a shallow prefix owned by
another provider; that does not mean the other provider can retrieve the reply.

## Routing precedence

CCH observes successful Responses JSON and SSE completions and records the
actual provider, endpoint, upstream transport, and a credential fingerprint.
The lookup is scoped to the authenticated API key plus response ID, rather than
the current client socket or prefix fingerprint. Redis shares it across workers
and reconnects; the local fallback is bounded to 16384 entries. Entries expire
after one hour, and Redis operations have a 250 ms budget.

A known reply owner overrides client session reuse, prefix affinity, and random
selection. Normal group, client, model, schedule, circuit, cost, and concurrency
checks still apply. An unavailable owner or changed upstream key requires
context recovery instead of sending the incremental body to a different account.
Continuations do not use Discovery, streaming hedge, or cross-provider retries.

Replies generated by HTTP fallback keep their next continuation on the same
HTTP endpoint, even when the client uses WebSocket. They are not upgraded to a
new upstream socket lacking the original response state. Unstored WS replies
still require their exact retained live socket; a stored ownership record does
not make that socket transferable across workers or client connections.
Likewise, routing an HTTP continuation to its owner does not create response
storage that the upstream has disabled; genuinely missing state still requires
full-input recovery. CCH does not force `store=true` or retain conversation bodies
in this ownership index.

The observer forwards the original bytes unchanged and uses bounded incremental
JSON facts, not a full copy of reasoning, output, or compaction envelopes.

## What recovery means

`Recovering failed WS continuation with full context` means CCH returns the
`previous_response_not_found` contract so the client can retry with full input.
It does not mean CCH possesses the missing conversation or internally replays it.

Only an actually dispatched failed continuation excludes that provider from
the next full-context request (short-lived, key/thread/model scoped). Both
top-level `error` and nested `response.failed` missing-response envelopes notify
this recovery state. A local missing socket or pre-dispatch route mismatch does
not accuse an uncontacted provider. Reusing a healthy provider for a full-context
replay after local socket loss is allowed and is not itself a failed recovery.

No origin can be inferred reliably for reply IDs created before this version,
outside CCH, or after the ownership cache expired. Stored requests with unknown
ownership retain legacy selection; unstored WS continuations require client
replay. Redis availability is needed to share HTTP origin across workers.

## Validation

```bash
bunx vitest run --config tests/configs/responses-ownership.config.mts --coverage
bunx vitest run --config tests/configs/responses-ws-recovery.config.mts
```

Coverage includes shallow competing affinity, changed client sessions, HTTP
fallback followed by a WS-client delta, API-key isolation, worker cache resets,
credential rotation, pinned endpoint failure without cross-provider retry,
nested recovery errors, and an ownership race checked immediately before WS
dispatch. These are local fixtures, not production traffic measurements.
